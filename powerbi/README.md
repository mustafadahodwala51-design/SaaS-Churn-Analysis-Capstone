# Power BI Dashboard - Build Guide

Dashboard specification for the SaaS churn capstone. This is a **written build
guide, not a `.pbix` file** - follow the steps below to reproduce the dashboard
in Power BI Desktop.

> **The data is synthetic.** It is generated by `data/generate_dataset.py` and
> describes no real company. Label the dashboard accordingly.

---

## 1. Data source

Use the **cleaned** tables, not the raw ones. The raw files contain deliberate
defects and will not load cleanly.

| Table | File | Grain | Rows |
|---|---|---|---|
| Customers | `data/cleaned/customers_clean.csv` | one row per customer | 1,250 |
| Monthly activity | `data/cleaned/customer_monthly_clean.csv` | one row per customer-month | 13,815 |
| Churn risk | `data/cleaned/churn_risk_scoring.csv` | one row per active customer | 820 |
| Monthly trend | `data/cleaned/analysis_monthly_trend.csv` | one row per month | 24 |

To get them in:

1. **Home → Get Data → Text/CSV**
2. Load each file, and in the query editor set the type to `Whole Number` for
   `mrr`, `seats`, `tenure_month`, `churn_flag`; `Decimal Number` for
   `adoption_rate`, `nps_score`, `discount_pct`; `Date` for `month_start`,
   `signup_date`, `churn_date`.
3. **Transform Data → Data type → Decimal Number** for the measures above if
   Power BI inferred `Whole Number`.
4. **Close & Apply**, then rename the queries to match the table names above.

### Relationships

```
customers[customer_id]  1  ->  *  monthly[customer_id]
customers[customer_id]  1  ->  0..1 churn_risk[customer_id]
```

Set the cross-filter direction to **Single** and mark the `customers` table as
the filter side. Do not create a relationship to `monthly_trend`; that table is
a pre-aggregated export used only for the KPI cards and the trend chart.

### A calendar table

```dax
Calendar =
CALENDAR ( DATE (2023, 1, 1), DATE (2024, 12, 31) )
```

Mark it as a date table, then set `customers[signup_date]` and
`monthly[month_start]` to relate to `Calendar[Date]` in an **Active**
relationship. Without this, time intelligence silently returns blanks.

## 2. Measures

Create these in a dedicated `_Measures` table. Keeping them in one place makes
them easy to review and reuse across pages.

### Headline KPIs

```dax
Total Customers = COUNTROWS ( customers )

Churned Customers =
CALCULATE ( [Total Customers], customers[churn_flag] = 1 )

Active Customers =
CALCULATE ( [Total Customers], customers[churn_flag] = 0 )

Logo Churn Rate =
DIVIDE ( [Churned Customers], [Total Customers] )
```

```dax
MRR (Current Month) =
CALCULATE (
    SUM ( monthly[mrr] ),
    monthly[month_start] = MAX ( monthly[month_start] )
)

ARR Run Rate = [MRR (Current Month)] * 12

ARPU = DIVIDE ( [MRR (Current Month)], [Active Customers] )

MRR Lost to Churn =
CALCULATE (
    SUM ( customers[mrr_at_signup] ),
    customers[churn_flag] = 1
)
```

### Revenue trend

```dax
MRR =
SUM ( monthly[mrr] )

MRR Prior Month =
CALCULATE ( [MRR], DATEADD ( 'Calendar'[Date], -1, MONTH ) )

MRR MoM Growth % =
DIVIDE ( [MRR] - [MRR Prior Month], [MRR Prior Month] )

Active Customers (Monthly) =
CALCULATE ( DISTINCTCOUNT ( monthly[customer_id] ) )

New Customers =
CALCULATE (
    COUNTROWS ( customers ),
    customers[signup_month] = MAX ( 'Calendar'[Date] )
)

Cancelled Customers =
CALCULATE (
    COUNTROWS ( customers ),
    customers[churn_flag] = 1,
    customers[churn_date] >= MAX ( 'Calendar'[Date] )
        && customers[churn_date] < EDATE ( MAX ( 'Calendar'[Date] ), 1 )
)
```

> **Why the churn measure is written this way.** Counting cancellations by
> `churn_date` inside the current month is correct, but it must *not* use
> `EDATE` on the month start for the customer count, because a cancellation dated
> the 1st of a month belongs to that month. The pattern above takes the whole
> month window from the first day to the same day next month.

> **`signup_cohort` is text and cannot be compared to a date.** The cleaned CSV
> stores it as `'2023-01'`, so the original
> `customers[signup_cohort] = MAX ( 'Calendar'[Date] )` was a type mismatch - it
> either raises an error or silently matches no rows, and the visual quietly
> shows zero. Add a calculated column on `customers` and use that instead:
>
> ```dax
> signup_month = DATEVALUE ( customers[signup_cohort] & "-01" )
> ```
>
> Make it a real date column, then relate `customers[signup_month]` to
> `'Calendar'[Date]` (many-to-one, single direction) so date slicers drive the
> cohort breakdown on page 6. With that relationship in place `New Customers`
> is simply the count of customers whose `signup_month` falls in the current
> month context, so the `CALCULATE` above is not even needed.

### Retention (survival, not share-of-base)

```dax
Customers At Risk (Tenure m) =
CALCULATE (
    COUNTROWS ( customers ),
    FILTER ( customers, customers[tenure_months] > m )
)

Cancellations At Tenure m =
CALCULATE (
    COUNTROWS ( customers ),
    FILTER ( customers, customers[churn_flag] = 1, customers[tenure_months] = m + 1 )
)

Cancellation Rate =
DIVIDE (
    [Cancellations At Tenure m],
    [Customers At Risk (Tenure m)]
)
```

> **This is the single most important modelling decision in the dashboard.**
> Dividing cancellations by everyone who ever signed up makes the retention
> curve collapse to zero at the right-hand edge, purely because the data stops
> there. Customers still active at the end of the period are **censored** -
> counted as at risk, never as churn. Use `tenure_months` from the cleaned
> customer table, which counts from 1; the monthly table counts from 0.

### Net Revenue Retention

NRR needs a *cohort* - the customers who were there at the start. Define that
cohort with a calculated column on `customers`, then use it in both the opening
and closing figures:

```dax
-- Calculated column on the customers table.
-- CALCULATE performs context transition here, so this evaluates per customer:
-- TRUE when that customer has a row in the Dec 2023 snapshot.
Active Dec 2023 =
CALCULATE (
    COUNTROWS ( monthly ),
    monthly[month_start] = DATE ( 2023, 12, 1 )
) > 0
```

```dax
NRR % =
VAR StartMRR =
    CALCULATE (
        SUM ( monthly[mrr] ),
        monthly[month_start] = DATE ( 2023, 12, 1 ),
        customers[Active Dec 2023] = TRUE ()
    )
VAR EndMRR =
    CALCULATE (
        SUM ( monthly[mrr] ),
        monthly[month_start] = DATE ( 2024, 12, 1 ),
        customers[Active Dec 2023] = TRUE ()
    )
RETURN
    DIVIDE ( EndMRR, StartMRR )
```

Expected result: `$836,792 → $756,792 = 90.4%`.

> **Two traps here.**
>
> 1. **Do not define the cohort with `tenure_months`.** A customer who signed up
>    in Nov 2023 and churned in Mar 2024 was in the Dec 2023 snapshot but has a
>    low tenure, so a tenure threshold silently drops them. Presence in the
>    monthly snapshot is the reliable test.
> 2. **Churned customers must stay in the denominator.** They are part of the
>    starting cohort, and they contribute 0 to the ending figure automatically
>    because they have no Dec 2024 row. Filtering the denominator down to
>    customers present in *both* months hides the churn and inflates NRR - on
>    this data it reports 108% instead of 90.4%.

### Segment churn

```dax
Churned (Segment) =
CALCULATE ( [Churned Customers], ALLEXCEPT ( customers, customers[plan_tier] ) )

Churn Rate (Plan) =
DIVIDE (
    CALCULATE ( [Churned Customers], ALLEXCEPT ( customers, customers[plan_tier] ) ),
    CALCULATE ( [Total Customers], ALLEXCEPT ( customers, customers[plan_tier] ) )
)
```

Repeat with `customers[acquisition_channel]`, `customers[region]`,
`customers[billing_cycle]`, `customers[company_size]` for the other segment
slicers. `ALLEXCEPT` keeps the segment filter and drops every other one, which
is what makes the rate correct rather than filtered by an unrelated slicer.

```dax
MRR Lost (Segment) =
CALCULATE (
    [MRR Lost to Churn],
    ALLEXCEPT ( customers, customers[plan_tier] )
)

Share of All Losses =
DIVIDE (
    [MRR Lost (Segment)],
    CALCULATE ( [MRR Lost to Churn], REMOVEFILTERS ( customers[plan_tier] ) )
)
```

> **The denominator must drop the segment filter, not re-apply it.** An earlier
> version of this measure used `ALLEXCEPT ( customers, customers[plan_tier] )`
> in *both* numerator and denominator. That is the same expression twice, so it
> returns 1 (100%) for every row and the visual is a flat line - no error, just
> a wrong answer. The numerator keeps the segment, the denominator removes it so
> it is the grand total across every plan.
>
> When the same measure is reused for a different breakdown, remove *that*
> column in the denominator instead - e.g. `REMOVEFILTERS ( customers[region] )`
> - and keep the numerator's `ALLEXCEPT` pointed at the matching column.

> **Show the rate and the revenue impact side by side.** They answer different
> questions and point at different segments. Starter has the highest churn rate
> (40.2%) but Business causes 40.7% of all MRR lost. A dashboard that shows only
> the churn rate sends the business after the wrong problem.

### Revenue at risk

```dax
High Risk MRR =
CALCULATE ( SUM ( churn_risk[final_mrr] ), churn_risk[risk_band] = "High risk" )

High Risk Accounts =
CALCULATE ( COUNTROWS ( churn_risk ), churn_risk[risk_band] = "High risk" )

Share of Active MRR at Risk =
DIVIDE ( [High Risk MRR], CALCULATE ( [MRR], customers[churn_flag] = 0 ) )
```

## 3. Pages

### Page 1 - Executive Summary

The page a stakeholder should be able to read in 30 seconds.

| Visual | Type | Fields |
|---|---|---|
| KPI row | Cards | Total Customers, Active Customers, MRR, ARR, ARPU, Logo Churn Rate, NRR % |
| The headline | Card + subtitle | MRR MoM Growth %, with a note on the last-6-month average |
| Revenue and customers | Combo chart | `monthly[month_start]` on axis; `MRR` as columns, `Active Customers (Monthly)` as line |
| Growth has stopped | Line | `MRR MoM Growth %` by month, with a reference line at 0% |
| Where revenue is leaking | Bar | `plan_tier` by `Share of All Losses` |
| What to do | Table | Top 5 recommendations, with the supporting number in a second column |

The subtitle matters as much as the chart. A flat MRR line with no context reads
as "stable"; the same line labelled "peak Oct 2024, −0.1% since, active
customers −3.1% from their September peak" reads as a ceiling.

### Page 2 - Churn Timing

| Visual | Type | Fields |
|---|---|---|
| Survival curve | Line | Tenure month on axis, `Cancellation Rate` as the value |
| Front-loaded loss | Card | % of all cancellations occurring before month 3 |
| Onboarding window | Table | Cancellation rate for tenure months 0-5, at-risk and cancellations shown |
| Cohort retention | Matrix | `signup_cohort` (rows) x tenure month (columns), value = % still subscribed |

Conditional formatting on the matrix: a 3-colour scale, red at 0 and green at
100. For cohorts that have not yet reached a tenure month, return `BLANK()` from
the measure rather than 0, so an unobserved month is never shaded as total
attrition.

```dax
Cohort Retention % =
VAR CohortSize =
    CALCULATE ( COUNTROWS ( customers ), ALLEXCEPT ( customers, customers[signup_cohort] ) )
VAR StillSubscribed =
    CALCULATE (
        DISTINCTCOUNT ( monthly[customer_id] ),
        ALLEXCEPT ( customers, customers[signup_cohort] ),
        monthly[tenure_month] = <tenure month from the matrix>
    )
VAR Observable =
    CALCULATE ( MAX ( customers[tenure_months] ), ALLEXCEPT ( customers, customers[signup_cohort] ) )
RETURN
    IF ( <tenure month from the matrix> > Observable,
         BLANK (),
         DIVIDE ( StillSubscribed, CohortSize ) )
```

### Page 3 - Segments

A slicer rail down the left for `plan_tier`, `acquisition_channel`, `region`,
`billing_cycle`, `company_size`, `engagement_band`, plus a month-range slicer.

| Visual | Type |
|---|---|
| Churn rate by segment | Bar, sorted descending, data labels on |
| MRR lost by segment | Bar, from the same segment field |
| Rate vs impact | Scatter: x = churn rate, y = share of MRR lost, size = customer count |
| Channel value table | Matrix: customers, churn %, avg discount, avg MRR, avg LTV |

The scatter is the point of the page: it makes visible that the
highest-churn segments are not the highest-cost ones.

### Page 4 - Early Warning Signals

| Visual | Type |
|---|---|
| Churned vs active | Clustered bar: mean `final_adoption`, `final_nps`, `final_tickets`, `discount_pct` by `churn_flag` |
| Engagement bands | Bar: churn rate by `engagement_band` |
| Warning checklist | Table: signal, direction, whether it is measured before cancellation |

Label the page **association, not causation**. Every signal here is recorded
before the cancellation, which makes it actionable, but low adoption may be a
symptom of a customer who was already leaving rather than a cause of it.

### Page 5 - Revenue at Risk

| Visual | Type |
|---|---|
| MRR by risk band | Stacked bar or treemap |
| Account table | Table: `customer_id`, plan, region, tenure, final MRR, adoption, NPS, risk score, band - sorted by score descending, top 200 |
| Band profile | Table or small multiples: mean adoption, NPS and tickets per band |

Enable the table's **Top N** filter (200 rows by risk score) and export
capability so a customer-success manager can work the list directly.

### Page 6 - Data Quality

Optional, and a good look in a review: the audit trail.

| Visual | Type |
|---|---|
| Issues found | Table from the cleaning log: issue, rows affected, treatment |
| Row reconciliation | Cards: raw rows, rows after dedup, customers, customer-months |
| Tenure cross-check | Card: mismatches between churn date and last active month (must be 0) |

## 4. Formatting and interaction

- One accent colour for "needs attention" (red), one for "healthy" (green), and
  grey for everything else. Colour should mean the same thing on every page.
- Format money as `$#,##0` and percentages as `0.0%`. Show a currency suffix on
  the first card in a row only, to reduce visual noise.
- Every chart gets a sentence title that states the finding, not the contents:
  "MRR growth has stalled while cancellations keep rising" beats
  "MRR by month".
- Add a page-level note on every page: *Synthetic data - see README.*
- Cross-filtering should be on between pages 2-5, off for the slicer rail, so
  clicking a plan does not empty the segment list.

### Reconciling before you share

The dashboard must agree with `python/data_analysis.py`. Check at minimum:

| Measure | Expected |
|---|---|
| Total customers | 1,250 |
| Churned customers | 430 |
| Active customers, Dec 2024 | 820 |
| Logo churn rate | 34.4% |
| MRR, Dec 2024 | $1,051,252 |
| ARR run rate | $12,615,022 |
| ARPU | $1,282 |
| NRR | 90.4% |
| MRR lost to churn | $304,928 |
| High-risk accounts / MRR | 273 / $508,458 |
| Tenure cross-check mismatches | 0 |

Then check the two things that a total can hide:

| Check | Expected | Why it is easy to get wrong |
|---|---|---|
| `Share of All Losses` sums to | 100% | A denominator that re-applies the segment filter returns 100% on every row |
| `New Customers` per month sums to | 1,250 | A text-to-date comparison matches no rows and reads as zero |
| Risk bands ordered worst-to-best | High = 15% adoption, Low = 66% | A flipped weight still produces three tidy, correctly-sized buckets |
| Cohort cells beyond each cohort's reach | blank | Painting them 0% reads as total attrition |
| `final_mrr` definition | mean of last 3 active months | The last month's value instead shifts 515 of 820 accounts |

`python/validate_sql.py` performs the equivalent check for the SQL layer. If the
Power BI numbers disagree with these, the cause is almost always a relationship
running in the wrong direction, a missing Active calendar relationship, or a
retention measure that divides by the wrong denominator.
