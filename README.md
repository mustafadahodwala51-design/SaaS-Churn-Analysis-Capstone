# SaaS Churn Analysis - Capstone Project

An end-to-end churn analysis of a simulated subscription business over
2023-2024, built as a data analytics portfolio project.

> **All data in this project is synthetic.** It is generated by
> `data/generate_dataset.py` and describes no real company, customer, or
> revenue. Findings are *associations observed in simulated data*, not causal
> conclusions.

---

## The short version

The business grew explosively through 2023 and then hit a ceiling. MRR reached
$1,052,669 in October 2024 and has been flat since, while active customers fell
3.1% from their September peak. Three things are driving that:

1. **New customers are worth much less.** Average MRR per new customer fell 58%
   from $1,349 in H1 2023 to $567 in H2 2024, and the Starter share of new
   logos rose from 32% to 48%.
2. **The existing base is shrinking.** NRR is 90.4% - churn gave back 16.4
   points of MRR, expansion recovered 6.8.
3. **Churn is front-loaded.** 38% of cancellations happen before month 3.

$508,458 of active MRR (49%) sits with 273 accounts showing measurable
pre-churn warning signs.

Full write-up: **[reports/Capstone_Report.md](reports/Capstone_Report.md)**

## Quick start

```bash
pip install -r requirements.txt

python data/generate_dataset.py     # writes the synthetic raw data
python python/data_analysis.py      # cleans, analyses, exports, charts, findings
python python/validate_sql.py       # confirms the SQL layer agrees with Python
python python/build_excel.py        # writes the Excel workbook
python python/build_notebook.py     # writes the notebook
```

The dataset is generated from a fixed seed, so every run produces identical
output. Expected console totals: 1,250 customers, 430 churned (34.4%), 820
active in December 2024, $1,051,252 MRR.

To read the notebook, open
`notebooks/Capstone_Analysis.ipynb` and use **Kernel → Restart & Run All**. It
is self-contained: it generates the data and runs the pipeline if the outputs
are missing.

## Method, in brief

**The raw data is dirty on purpose.** Twelve categories of defect are seeded -
duplicate rows, mixed date formats, currency stored as text, missing values,
negative MRR, 50,000-seat outliers, `EMEA` vs `Europe`, adoption rates on two
different scales. Each gets one deliberate, documented treatment in
`python/data_analysis.py`.

**Retention is a survival calculation.** A customer is at risk in month *t* only
if they were still subscribed after month *t*. Customers still active at the end
are censored - at risk, never churned. Dividing cancellations by everyone who
ever signed up is the most common error in churn analysis: it drives the curve
to zero at the right-hand edge purely because the data stops there.

**Cohort averages use only observable cohorts.** A cohort that signed up last
month has not been tested at month 12. Those cells are left blank, not filled
with 0%, which would falsely read as total attrition.

**Tenure is recomputed** from the monthly activity table and cross-checked
against the reported value, because tenure drives retention, the risk score and
lifetime value.

**The analysis is implemented twice** - Python and SQL - and
`python/validate_sql.py` compares them measure by measure. Both agree.

## Two bugs worth reading about

Both were silent: each produced a clean run and plausible-looking output.

**Mixed date formats.** `churn_date` appears as both `2024-10-01` and
`01/08/2023`. Parsed with pandas' `format="mixed"`, ambiguous values are read
month-first *regardless of* `dayfirst=True`, so 1 August became 8 January. 137
of 430 cancellations appeared in January 2023. It was caught by cross-checking
each cancellation date against the customer's last active month, which must be
exactly one month earlier: the first run of that check reported **382
mismatches out of 430**. It is now a permanent pipeline assertion.

**NRR inflated by an inner join.** The SQL version originally reported NRR of
108% because churned customers were dropped from the denominator, hiding the
churn entirely. The correct figure is 90.4%. This is the same class of error as
the date bug, in a different language - which is why the SQL layer is
reconciled against Python rather than trusted.

The lesson generalises: **validate the result, not the absence of an exception.**

## Limitations

1. The data is simulated; the findings demonstrate method, not reality.
2. All relationships are **associations, not causes**. No intervention was
   tested and no causal claim is supported.
3. No control group, so no experiment can be inferred.
4. Late-2024 cohorts have not reached month 12 - their retention is unknown,
   not good, and is left blank throughout.
5. Churn reasons are self-reported and indicative only.
6. The risk score is rule-based, chosen for explainability over accuracy. It
   ranks accounts; it is not a validated probability of churn.
7. Churn is treated as final - reactivation, upgrades and downgrades are not
   modelled.
